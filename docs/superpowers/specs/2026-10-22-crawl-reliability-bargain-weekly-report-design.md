# 크롤링 안정성 · 진짜 급매 점수 · 주간 리포트 설계

작성일: 2026-10-22 · 대상: naver-real-estate v1(`main`, 주거용) + v2(`version-2.0`, 상업용)

## 왜 하는가

- 2026-10-21~22 이틀 동안 맥미니 인터넷이 끊겨(10/20 17:55 ~ 10/22 15:24) 9시·10시 크롤링이 모두 실패했다. 아무도 몰랐고 사람이 직접 재실행해야 했다.
- 크롤러는 페이지 요청이 실패하거나 네이버가 429(요청 제한)로 막으면 "더 이상 데이터 없음"으로 보고 조용히 멈춘다. 매물이 빠져도 티가 안 난다.
- 급매 태그가 붙어 있어도 실제로 싼지는 알 수 없다. 같은 단지 시세보다 확실히 싼 매물을 골라 보고 싶다.
- 시장 흐름(총 급매 변동폭, 주요 단지)을 매주 휴대폰으로 받아 보고 싶다.

**성공 기준:** 인터넷이 몇 시간 끊겨도 같은 날 안에 자동 복구되고, 끝내 실패하면 텔레그램으로 알 수 있다. 매주 월요일 텔레그램으로 리포트가 온다. 사이트에서 "진짜 급매"만 골라 볼 수 있다.

## 목표 / 비목표 / 실패로 간주하는 것

목표
1. 페이지 요청 실패·429를 재시도하고, 끝내 실패한 조합 수를 집계해 결과에 반영 (v1, v2)
2. 하루 3회 시도(첫 실행 + 재시도 2회), 이미 성공한 날은 재시도 생략 (v1, v2)
3. 실패/복구/부분 누락을 텔레그램으로 알림 (v1, v2)
4. 진짜 급매 점수: 저장 시 계산, 사이트 배지 + 필터 (v1만)
5. 주간 리포트 자동 생성·텔레그램 전송 (v1만)

비목표
- 상업용(v2)의 진짜 급매 점수·주간 리포트 (상업용은 단지 개념이 약하다 — *내 판단*)
- 단지 고유번호(complexNo) 수집. 같은 구에 이름이 같은 단지는 하나로 합쳐진다 (알려진 한계)
- 텔레그램 봇 신규 생성, 매일 성공 알림

실패로 간주하는 것
- 정상 성공한 날 알림이 와서 귀찮아지는 것
- 재시도 때문에 같은 날 크롤링이 두 번 저장되는 것 (오늘 성공했으면 반드시 건너뛴다)
- 알림 전송 실패가 크롤링 자체를 실패시키는 것
- 기존 동작(목록·지도·알림 API 응답)이 의도치 않게 바뀌는 것 — 특성화 테스트로 확인

## 결정된 사항 (사용자 결정)

- 진짜 급매 기준: 비교 대상 중앙값보다 **10% 이상** 싸면 진짜 급매
- 주간 리포트 내용: 총 급매 변동폭 → 급매 늘어난/줄어든 단지 → 진짜 급매 상위 매물(링크 포함). 테스트 메시지(2026-10-22 발송) 형식 그대로 승인
- 재시도 시각: 주거용 9시 + 12시·15시. 15시까지 실패하면 실패 알림, 실패 후 복구되면 복구 알림, 정상일은 알림 없음
- 실패 조합이 전체의 20% 초과면 그날 결과를 실패 처리(기존 데이터 유지), 그 이하면 저장하고 누락 수를 알림
- 상업용(v2)에도 재시도·알림 적용
- 텔레그램은 기존 Hermes 봇 재사용 (`~/.hermes/.env`의 `TELEGRAM_BOT_TOKEN`, `TELEGRAM_HOME_CHANNEL`)

## 설계

### 1. 페이지 요청 실패 처리 (crawler.py, v1·v2)

- `JS_FETCH_PAGE`가 성공 시 `{"ok": true, "data": ...}`, HTTP 오류 시 `{"ok": false, "status": <코드>}`, 네트워크/타임아웃 시 `{"ok": false, "status": 0}`을 돌려준다.
- 실패한 페이지는 최대 3번 재시도: 429는 30·60·120초, 그 외(0, 5xx)는 2·5·15초 대기. 401/403 등 기타 4xx는 재시도하지 않는다 (토큰 문제는 기다려도 안 풀린다).
- 재시도 후에도 실패하면 그 조합은 "실패 조합"으로 세고 WARNING 로그를 남긴다. 이미 받은 페이지의 매물은 그대로 쓴다.
- `page.evaluate` 자체 예외도 같은 실패로 취급한다(지금은 조용히 break).
- `crawl_all()` 결과에 `failed_combos`, `total_combos`를 추가한다. `failed_combos / total_combos > 0.2`면 `status=failed`로 기록하고 매물은 저장하지 않는다(기존 데이터 유지). 이미 있는 `MIN_LIVE_CRAWL_RATIO` 검사는 그대로 둔다.
- `crawl_history` 스키마는 바꾸지 않는다. 실패 조합 수는 결과 dict·로그·알림으로만 전달한다.

### 2. 자동 재시도 (scripts/, v1·v2)

- `run_remote_crawl.sh`: 네트워크 대기 12회×5초(약 1분) → 최대 15분, DB DNS 대기 12회×10초(약 2분) → 최대 15분으로 늘린다.
- `run_remote_crawl.py`에 `--skip-if-succeeded-today` 추가: 시작 시 DB에서 오늘(KST) `status='success' AND source='naver'` 기록이 있으면 로그만 남기고 종료(exit 0).
- launchd `StartCalendarInterval`을 배열로 바꿔 하루 3회 실행: 주거용 09:00·12:00·15:00, 상업용 10:00·13:00·16:00. 재시도 슬롯과 첫 실행 모두 `--skip-if-succeeded-today`를 쓴다 (첫 실행 시점엔 기록이 없으니 자연히 크롤링한다).
- `install_launchd_crawl.py`에 `--retry-hours`(예: `12,15`) 추가, 생성 plist에 위 인자를 넣는다. 설치 시 기존 plist의 DB URL을 그대로 쓴다.
- "오늘"은 맥미니 로컬 시각(KST) 기준 날짜다. `crawl_history.crawled_at`은 크롤러가 `datetime.now()`(로컬, naive)로 쓰므로 그 날짜와 비교한다 — *내 판단*.
- 앞선 실행이 아직 도는 중에 재시도 시각이 되면 launchd가 같은 작업을 겹쳐 띄우지 않는다(건너뛴 슬롯은 실행되지 않음). 추가 잠금은 만들지 않는다 — *내 판단*.
- v2는 DB 스키마 `commercial_v2`를 쓰므로 같은 코드로 상업용 기록만 확인된다.

### 3. 텔레그램 알림 (notifier.py 신규, v1·v2)

- `send_telegram(text)`: 환경변수 `TELEGRAM_BOT_TOKEN`/`TELEGRAM_CHAT_ID`가 있으면 사용, 없으면 `~/.hermes/.env`에서 `TELEGRAM_BOT_TOKEN`/`TELEGRAM_HOME_CHANNEL`(+ 선택 `TELEGRAM_HOME_CHANNEL_THREAD_ID`)을 읽는다. 설정이 없거나 전송이 실패하면 WARNING 로그만 남기고 False를 반환한다 — 절대 예외를 던지지 않는다.
- 상태 파일 `logs/crawl_alert_state.json`: 날짜별 시도/실패 기록과 "못 보낸 알림"을 저장한다. DB가 아니라 로컬 파일인 이유: 인터넷·DB가 끊겨도 기록돼야 하기 때문.
- 알림 규칙 (`run_remote_crawl.py`가 판단):
  - 실패(크롤 실패, DB 연결 실패, 예외 포함) & 현재 시각이 마지막 슬롯 이후(`--final-hour`, 주거용 15·상업용 16) → "❌ 오늘 크롤링 최종 실패" 알림
  - 성공 & 오늘 앞서 실패한 시도가 있었음 → "✅ 크롤링 복구" 알림
  - 성공 & 실패 조합 1개 이상 → "⚠️ 일부 누락 N/M 조합" 알림 (복구 알림과 겹치면 한 메시지로)
  - 알림 전송에 실패하면 상태 파일에 남겨 두고, 다음 실행 시작 시 먼저 보낸다
- 메시지 맨 앞에 `[주거용]` / `[상업용]` 표시.

### 4. 진짜 급매 점수 (database.py, app.py, static/js, v1)

- `listings`에 컬럼 2개 추가 (init_db의 기존 ALTER TABLE 방식): `bargain_discount REAL`(중앙값 대비 할인율, 0~1), `bargain_basis TEXT`(`'same_area'` 또는 `'complex_m2'`).
- `insert_listings()`가 세션 매물 전체로 계산해 함께 저장한다. 대상: 매매, 아파트·오피스텔, 건물명이 일반 명칭(`GENERIC_BUILDING_NAMES`)이 아님, 면적 값 있음, `price_sort_value > 0`.
  - 1순위: 같은 (구, 단지명, 평형 타입) 매물이 3건 이상이면 가격 중앙값과 비교 (`same_area`)
  - 2순위: 아니면 같은 (구, 단지명)의 ㎡당 가격(평형 타입 앞 숫자) 중앙값이 3건 이상일 때 비교 (`complex_m2`)
  - 할인율은 음수(더 비쌈)도 저장한다. 진짜 급매 판정은 **0.10 ≤ 할인율 ≤ 0.40**. 0.40 초과는 지분·오류 의심이라 배지·필터에서 제외한다.
- 기존 매물(오늘 세션)은 배포 후 한 번 `scripts/backfill_bargain_scores.py`로 채운다 — 운영 DB에 쓰는 작업.
- API: `/api/listings`, `/api/map-listings`에 `bargain_only=true` 추가. `/api/listings` 응답에 `bargain_count` 필드 추가(기존 필드는 그대로).
- 사이트: 매물 카드에 `💎 단지 중앙값 −14%` 배지(기준이 complex_m2면 툴팁에 "단지 ㎡당 가격 기준"), 상단 통계 카드 줄에 "진짜 급매" 카드 추가(클릭 시 필터, 기존 가격인하 카드와 같은 방식).

### 5. 주간 리포트 (scripts/weekly_report.py 신규, v1)

- 2026-10-22 테스트 스파이크와 같은 메시지 형식. 진짜 급매는 저장된 `bargain_discount`를 읽어 사이트와 같은 값을 쓴다.
- 비교 대상: 최신 성공 세션 vs 7일 전(±12시간 이내 가장 가까운 이전) 성공 세션. 7일 전 세션이 없으면 가장 오래된 가용 세션과 비교하고 기간을 그대로 표시한다.
- 단지 변동: `crawl_building_stats` 두 세션 비교, 증가 상위 5 / 감소 상위 5.
- launchd `com.lunadad.naver-real-estate-weekly-report`: 매주 월요일 10:30. 월요일 크롤링이 아직 성공 전이면 직전 성공 세션 기준으로 보낸다(메시지에 기간 표시). `--dry-run`이면 출력만.
- 설치: `scripts/install_launchd_weekly_report.py`.

## 배포 (구현·테스트 완료 후 진행)

1. v1 기능 브랜치 → `main` 병합, v2 기능 브랜치 → `version-2.0` 병합, 둘 다 origin에 push
2. 주거용 크롤 폴더(`~/workspace/naver-real-estate`, 현재 detached HEAD)를 새 `main`으로 이동. 상업용 폴더(`naver-real-estate-v2`)는 `version-2.0` 그대로라 병합으로 반영됨
3. 두 크롤 plist 재설치(하루 3회), 주간 리포트 plist 설치
4. v1 사이트 `vercel --prod` 배포 (main push로 자동 배포 안 됨)
5. `backfill_bargain_scores.py`로 오늘 세션 점수 채우기
6. 텔레그램 테스트 알림 1회 전송으로 경로 확인

## 테스트

- 기존 73개 테스트 + 특성화 골든 유지. 의도적으로 허용하는 골든 변화는 (a) 크롤러 결과의 실패 조합 처리, (b) 매물 행의 `bargain_discount`/`bargain_basis` 컬럼과 목록 응답의 `bargain_count` **추가**뿐이다. 기존 필드 값이 하나라도 바뀌면 버그로 본다 — 골든 재생성 전후 diff에 추가만 있는지 확인한다.
- 크롤러: 가짜 Playwright로 429 후 성공, 끝내 실패, evaluate 예외, 20% 경계(정확히 20%는 성공, 초과는 실패) 확인. `time.sleep`은 mock.
- 재시도/알림: 상태 파일·시각·텔레그램 전송을 주입 가능하게 만들어 규칙별 단위 테스트.
- 진짜 급매: 같은 평형/단지 ㎡당 기준 선택, 3건 미만 제외, 일반 명칭·면적 없음·전월세 제외, 0.10/0.40 경계, API 필터·배지 필드.
- 주간 리포트: SQLite 테스트 DB로 메시지 생성 결과 검증 (전송은 mock).
